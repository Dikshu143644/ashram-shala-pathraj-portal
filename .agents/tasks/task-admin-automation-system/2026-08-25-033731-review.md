# Admin automation system v2: fixes applied, gallery safety column mismatch remains

All five issues from the first review pass have been addressed: the activity middleware now calls `readSession(req)` directly, Gemini Vision receives proper base64 `inline_data`, every error path in content-safety is fail-closed, the gallery safety check updates `gallery_images.safety_status` server-side, and the digest timer exposes a `stopDigestTimer()` handle. The code is in a substantially better state.

Watch for: the server-side safety status update uses `.eq('image_url', ...)` but the gallery table column is `url` — the update never matches any row (confirmed); flagged images remain publicly visible because the public gallery endpoint does not filter by `safety_status` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The content-safety route attempts to write `safety_status` to the `gallery_images` table by matching on a column called `image_url`, but the table schema defines the column as `url`. Both the "flagged" and "approved" update paths silently fail (Supabase returns zero affected rows, no error thrown). Until the `.eq()` predicate is corrected, no image will ever show an accurate safety badge, and the public gallery has no mechanism to hide flagged content from non-admin visitors.

The public `/api/gallery` endpoint returns all images regardless of safety status. Even once the column mismatch is fixed, a flagged image will be visible on the school website until an admin deletes it. Adding a `.neq('safety_status', 'flagged')` filter (or equivalent) to the public query would enforce moderation at the data layer.

## Gallery safety status column mismatch

The `gallery_images` table was created in `202506190001_fix_all_issues.sql`:

```sql
CREATE TABLE IF NOT EXISTS gallery_images (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  url TEXT NOT NULL,
  caption TEXT,
  uploaded_by UUID REFERENCES auth_users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

The column holding the image URL is `url`. The activity-monitor migration adds `safety_status` and `safety_score` columns to this table. The upload route in `data.ts` inserts into the `url` column:

```typescript
.insert({ url: publicUrl, storage_path: storagePath, ... })
```

But `content-safety.ts` matches against a non-existent `image_url` column:

```typescript
await supabase
  .from('gallery_images')
  .update({ safety_status: 'flagged', safety_score: result.score })
  .eq('image_url', imageUrl.trim());  // ← should be 'url'
```

Supabase's PostgREST layer treats an unknown column in a filter as matching zero rows (no error raised). The `updateError` check catches Postgres errors but not zero-match conditions. Both the "flagged" path (line 145) and the "approved" path (line 172) have this bug.

## Public gallery does not exclude flagged content

The public endpoint that serves the school gallery is:

```typescript
app.get('/api/gallery', async (_req, res) => {
  const { data, error } = await supabase
    .from('gallery_images')
    .select('*')
    .order('created_at', { ascending: false });
  ...
});
```

There is no filter on `safety_status`. Once the column mismatch above is fixed, successfully flagged images will still appear on the public-facing gallery. The moderation flow only becomes effective when the public query excludes flagged rows.
