# Admin automation system: WhatsApp notifications, content moderation, activity monitor, and admin routes

This change adds four server modules — a WhatsApp notification service, a Gemini Vision content safety endpoint, an activity logging middleware with a 15-minute digest, and a full set of admin API routes for event approval, audit logs, application management, and parent-student linking. The frontend SuperAdminCenter is rewired from hardcoded mock data to real API calls with filtering, pagination, and safety badges. A migration creates the backing `activity_logs` and `events` tables plus alters `gallery_images` and `applications`.

Watch for: the activity log middleware will never log anything because `authSession` isn't populated at the point it runs (confirmed); the content safety agent passes the image URL as a plain text string rather than as a Gemini Vision `image_url` part, so it isn't actually performing image analysis (confirmed); the content moderation is fail-open by design — API errors, missing keys, and parse failures all auto-approve (confirmed, deliberate but worth noting).

**Verdict**: NEEDS_CHANGES

## High-level view

The activity monitor middleware is placed before route handlers but reads `req.authSession`, which is only set by the per-route `requireSession()` guard. It will therefore always see `undefined` and skip every request. The middleware needs to call `readSession(req)` itself to decode the session cookie.

The Gemini Vision integration constructs a request body with `inline_data: undefined` and `file_data: undefined` placeholder parts, then passes the image URL as a text instruction. Gemini's vision models require either `inline_data` (base64) or a `file_data` (GCS URI) part to analyse an image; sending the URL as text means the model receives a text-only prompt and cannot inspect the image pixels. The safety check will return plausible-looking JSON but is not actually performing visual analysis.

Content moderation is fail-open across every error path: missing API key auto-approves, HTTP errors auto-approve, JSON parse failures auto-approve. Combined with the broken image analysis above, the content safety feature provides no blocking protection in any configuration.

The `setInterval` digest timer has no cancellation mechanism, which prevents clean server shutdown and complicates testing.

## Activity middleware session ordering

The middleware is mounted in `app.ts` at line 57 (`app.use('/api', activityLogMiddleware(supabase))`), before any route handler registers. The code inside reads:

```typescript
const session = authReq.authSession;
if (!session || session.role === 'web_creator') {
  next();
  return;
}
```

`authSession` is only ever set inside `requireSession()`:

```typescript
(req as AuthenticatedRequest).authSession = session;
```

Since `requireSession` is a per-route guard (applied to individual routes below the middleware), `authSession` is always undefined when the middleware runs. The guard returns early on `!session`, meaning nothing is ever logged.

The fix is to import `readSession` and call it directly:

```typescript
const session = readSession(req);
```

This decodes the HMAC-signed cookie without enforcing authentication (unauthenticated requests still pass through, they just don't get logged).

## Gemini Vision image delivery

The Gemini `generateContent` API expects multimodal content in specific part types. For URL-based images, the correct format is a `file_data` part with a `file_uri` field (requires a Cloud Storage URI) or an `inline_data` part with base64-encoded bytes and a MIME type. The current code sends:

```typescript
parts: [
  { text: prompt },
  { inline_data: undefined, file_data: undefined },
  { text: `Image URL to analyze: ${imageUrl}` },
]
```

Gemini will interpret this as a text-only request. It may produce a JSON response (it's been prompted to), but the safety score will not reflect actual image content — it will be hallucinated from the URL text. For proper vision analysis, the server needs to fetch the image, convert to base64, and send as `inline_data: { mime_type: "image/jpeg", data: base64String }`.

## Fail-open content safety posture

Three distinct failure paths all resolve to `safe: true`:

| Condition | Return |
|-----------|--------|
| No `GEMINI_API_KEY` | `{ safe: true, score: 1.0 }` |
| Non-200 Gemini response | `{ safe: true, score: 0.8 }` |
| JSON parse failure / caught exception | `{ safe: true, score: 0.8 }` |

Combined with the fact that the image isn't actually analysed even when the API is working, the entire content safety pathway currently provides no protection. If the intent is to block harmful school content, this should be fail-closed (reject with a "please retry" message) at minimum for the malformed-request path.

## Gallery safety enforcement gap

In `SuperAdminCenter.tsx`, the safety check runs client-side after upload:

```typescript
const safetyRes = await fetch('/api/content/analyze', { ... });
const safetyData = await safetyRes.json();
if (safetyRes.ok && safetyData.safe === false) {
  setSafetyWarning(...);
}
```

There's no server-side hook that marks or removes the image in the `gallery_images` table on an unsafe result. The migration adds `safety_status` and `safety_score` columns but nothing writes to them during the upload or analysis flow. A user who ignores the warning (or bypasses the frontend entirely by calling the gallery API directly) stores the image without any moderation gate.

## Digest timer lifecycle

```typescript
function startDigestTimer(supabase: SupabaseClient): void {
  setInterval(() => {
    void sendActivityDigest(supabase);
  }, DIGEST_INTERVAL_MS);
}
```

The interval handle is discarded. In test or multi-instance environments this timer cannot be stopped, and during graceful shutdown it prevents the Node process from exiting. Exposing the interval ID and clearing it in a shutdown handler is the standard approach.
