# Auralis monochrome redesign + WhatsApp AI chatbot

A complete visual overhaul replaces the emerald/gold Material 3 design system with a minimal monochrome palette (black, #F7F7F5, #FCFCFB, subtle grey borders), and introduces a Gemini-powered WhatsApp chatbot backend with phone-verified access. The redesign adds a new `LandingPage` as the unauthenticated entry point, replaces all color tokens in `index.css`, reskins every portal component to the new palette, and swaps fonts to Geist + Noto Sans Devanagari. The chatbot adds `server/whatsapp-bot.ts` with two new endpoints (`/api/whatsapp/verify` and `/api/whatsapp/chat`) gated behind session auth and rate limiting, plus a rewritten `WhatsAppHub.tsx` frontend with a phone verification flow and real-time Gemini responses.

Watch for: The phone verification step doesn't actually gate chatbot access — any authenticated user can call `/api/whatsapp/chat` without ever calling `/verify` (confirmed). The Gemini API key is passed as a URL query parameter, which will appear in server logs and potentially in error traces (confirmed). No conversation history is maintained between requests, so the bot cannot follow multi-turn context (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The design token swap is thorough — backwards-compatible CSS variable aliases (`--navy`, `--gold`, etc.) now point to black/monochrome values, meaning untouched components automatically inherit the new palette without code changes. There's a duplicated `--transition-fast` / `--transition-normal` definition in `:root` that should be cleaned up (likely a merge artifact).

The WhatsApp chatbot backend integrates Gemini through a direct HTTPS fetch (no SDK), enriching the system prompt with per-user student data from Supabase. The architecture relies entirely on a static system prompt for school knowledge — no RAG, no embeddings — which is appropriate for the fixed-data use case but means hallucination is bounded only by the model's tendency to invent details outside the prompt.

The phone verification endpoint checks the `auth_users` table but the result is never persisted or checked by the chat endpoint. Verification is cosmetic — the frontend enforces it, but the API does not. An authenticated user (or a script with a valid session cookie) can skip verification entirely and chat directly.

## Phone verification is a UI gate, not an API gate

The `/api/whatsapp/verify` endpoint confirms that a phone number exists in `auth_users` and returns `{ verified: true }`. The frontend stores this in React state (`isVerified`) and conditionally renders the chat UI. However, the `/api/whatsapp/chat` endpoint only checks `requireSession(authenticatedRoles)` — it never verifies that the caller previously passed phone verification.

```typescript
// whatsapp-bot.ts line ~200
app.post(
  '/api/whatsapp/chat',
  requireSession(authenticatedRoles), // <-- any logged-in user can hit this
  chatLimit,
  chatGate,
  async (request: Request, res: Response) => { ... }
);
```

Any authenticated user (web_creator, principal, teacher, clerk, parent) can call the chat endpoint directly. If the intent is to restrict chatbot access to verified parents, the server must persist the verification state — for example, setting a flag in the session after `/verify` succeeds and checking it in the chat middleware.

## Gemini API key in URL query parameter

```typescript
`https://generativelanguage.googleapis.com/v1beta/models/${model}:generateContent?key=${encodeURIComponent(apiKey)}`
```

The key appears in any HTTP access log, proxy log, error trace, or network inspector between the server and Google's endpoint. The Gemini API also accepts `x-goog-api-key` as a request header, which keeps the key out of URLs.

## Stateless chat — no multi-turn context

Each call to `/api/whatsapp/chat` sends a single `message` string. The `WhatsAppHub.tsx` frontend maintains a `messages` array in React state, but this is never sent to the backend. Each API call is independent:

- The bot cannot reference its own prior answers
- The bot cannot resolve pronouns ("what about that?", "tell me more")
- The bot cannot maintain context across a series of questions about the same student

Sending the last 5-10 messages as `contents` in the Gemini request body would enable multi-turn conversation without server-side storage.

## PostgREST filter interpolation in phone verify

```typescript
const normalized = phoneNumber.replace(/[\s\-()]/g, '').trim();
// ...
.or(`mobile_number.eq.${normalized},mobile_number.eq.+91${normalized.slice(-10)}`)
```

After normalization, `normalized` could still contain characters like commas, periods, or other non-digit characters (the regex only removes whitespace, `-`, `(`, `)`). The length check (10-15 characters) provides some bounds but doesn't guarantee digits-only. Adding a `/^\+?\d{10,15}$/` check after normalization would close this gap.

## Silent failure in student context fetch

`fetchStudentContext` catches all errors and returns an empty string. A parent asking "what's my child's attendance?" will get a generic response with no indication that data fetching failed. The bot's system prompt instructs it to say "I am checking records," but it has no signal to distinguish "no data found" from "query failed." Consider logging the error and optionally injecting a `[student data unavailable]` marker into the prompt so the bot can respond honestly.

## Duplicated CSS variables

In `src/index.css` `:root`, `--transition-fast` and `--transition-normal` appear twice with conflicting values:

- First: `--transition-normal: 200ms cubic-bezier(0.4, 0, 0.2, 1)`
- Second (end of block): `--transition-normal: 250ms cubic-bezier(0.2, 0.8, 0.2, 1)`

The second silently wins. This is likely a merge artifact — remove one definition.
