# Auralis redesign + WhatsApp AI chatbot (v2)

All seven issues from the v1 review have been addressed: phone verification is enforced server-side via an in-memory `verifiedUsers` set, the Gemini API key moved to an `x-goog-api-key` header, conversation history is sent as the last 6 messages, Gemini error bodies are logged, phone number validation uses a strict regex after normalization, duplicate CSS variables are removed, and placeholder contact details have realistic numbers.

Watch for: The frontend includes the current user message in the `history` array, then the backend appends the same message again — the user's input appears twice in every Gemini request (confirmed). The in-memory `verifiedUsers` Set won't persist across Vercel serverless cold starts, meaning verification can fail intermittently in production (confirmed). History entries from the client have no per-entry length cap, allowing prompt-size inflation past the 500-char message limit (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The multi-turn history implementation has a double-send bug: the frontend builds `updatedMessages` (which already contains the new user message) and sends its last 6 entries as `history`, while the backend unconditionally appends the same `message` text again before calling Gemini. Every request will contain the user's latest input twice in the `contents` array, confusing the model's conversational context.

The `verifiedUsers` in-memory Set is a module-level singleton. On Vercel serverless, each invocation may or may not reuse the same runtime instance. A user who verifies on one instance and chats on a different one will receive a 403. This is architecturally incompatible with the Vercel deployment target defined in `vercel.json`.

History entries are validated for shape (must have `role` and `text` strings) but not for size. A malicious client can send 6 history entries of arbitrary length, inflating the Gemini prompt far beyond what `MAX_MESSAGE_LENGTH` intends to bound.

## Duplicate user message in the Gemini request

The frontend constructs:

```typescript
const updatedMessages = [...messages, { role: 'user', text: userMessage }];
const history = updatedMessages.slice(-6).map(msg => ({
  role: msg.role === 'user' ? 'user' : 'model',
  text: msg.text,
}));
// Sends both `message: userMessage` and `history` (which contains userMessage as its last entry)
```

The backend then:

```typescript
const contents = [
  ...history.map(msg => ({ role: msg.role, parts: [{ text: msg.text }] })),
  { role: 'user', parts: [{ text: message }] },  // duplicate
];
```

The simplest fix is for the frontend to send `updatedMessages.slice(-(6 + 1), -1)` — the 6 messages *before* the current one — since the backend already appends the current message.

## In-memory verification on serverless

The comment on the `verifiedUsers` Set acknowledges it clears on restart:

```typescript
// In-memory set of user IDs that have completed phone verification this session.
// Cleared on server restart, which is acceptable since verification is lightweight.
const verifiedUsers = new Set<string>();
```

On Vercel serverless, "restart" effectively means "any request that doesn't hit a warm instance." Two sequential requests from the same user can land on different isolates. The verify call adds the user to instance A's Set; the subsequent chat call might land on instance B where the Set is empty, returning 403. The experience will be unpredictable — sometimes working, sometimes not — depending on Vercel's instance scheduling.

Options: persist the flag in a Supabase table (simplest), attach it to the session payload stored in the cookie, or remove server-side verification and treat the existing session auth as sufficient gate.

## Unbounded history entry length

The `message` field is validated:

```typescript
if (message.length > MAX_MESSAGE_LENGTH) { ... }
```

But `history` entries are only checked for type (`string`) not size. Since the client controls `history`, an attacker could send:

```json
{ "message": "hi", "history": [{ "role": "user", "text": "<100KB string>" }, ...] }
```

The Express body limit is 10KB which partially mitigates this, but 10KB across 6 entries still permits ~1600 chars each — well above the 500-char message cap. Add a per-entry truncation when iterating:

```typescript
conversationHistory.push({ role, text: (entry as { text: string }).text.slice(0, MAX_MESSAGE_LENGTH) });
```
