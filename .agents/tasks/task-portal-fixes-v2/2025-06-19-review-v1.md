# Portal enhancements: gallery, real contacts, AI student context, live audit logs

This change adds several public-facing features to the school portal: a gallery section with admin CRUD, real contact information in the footer (personal phone numbers, WhatsApp, Google Maps embed), an AI assistant enhancement that fetches and injects a parent's linked student records into the LLM prompt, and replacement of mock audit log data with live `security_logs` queries. A Supabase migration creates the `gallery_images` and `ai_passwords` tables.

Watch for: student PII (names, guardian details, mobile numbers, village) is serialized into LLM prompts with no field filtering (confirmed); gallery image URLs are stored without protocol validation, enabling potential stored XSS via `javascript:` URIs rendered in `<img src>` (confirmed); the gallery section silently disappears from the landing page when zero images exist, with no empty state or admin upload path from the public page (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The AI assistant now fetches the full `students` row (`select('*')`) for any parent user and injects it verbatim into the system prompt. This passes PII—guardian mobile numbers, village names, full names of minors—to a third-party LLM provider. The volume of data is small (bounded by `parent_student_ids` length), but the data classification is high for a government school serving tribal minors.

The gallery backend is well-guarded by role checks, rate limits, CSRF protection, and UUID validation. The one gap is URL content validation: any string up to 2048 characters is accepted and later rendered as an `<img src>`. If an attacker with `web_creator` credentials submits a `javascript:` or `data:text/html` URI, the frontend renders it without sanitization.

The footer now contains real personal phone numbers (principal, clerk) and a personal Gmail address hardcoded in the JSX. These are intentional per the task description, but the numbers are now in the public git history permanently.

## Student data injection into LLM prompts

The `/api/ai-chat` handler queries `auth_users` for the authenticated user's `parent_student_ids`, then fetches all matching rows from `students` with `select('*')` and serializes the result into the system prompt:

```typescript
studentContext = `\n\nThe user is a parent. Their linked student data:\n${JSON.stringify(students, null, 2)}`;
```

The students table schema (inferred from the POST endpoint's `allowedFields`) includes: `full_name`, `standard`, `date_of_birth`, `blood_group`, `apaar_id`, `mobile_number`, `guardian_name`, `guardian_mobile`, `guardian_relation`, `village`, `taluka`, `district`, `pincode`, `status`. All of these are sent to whichever LLM provider responds (Gemini, OpenAI, or Anthropic).

For a government school serving tribal minors under the Tribal Development Department, this is a data classification concern. The APAAR ID (India's unique student identifier), guardian mobile number, and village-level location of minor tribal children should not transit through third-party AI providers without explicit policy allowing it.

The fix is straightforward: replace `select('*')` with an explicit column list that includes only what the AI needs to provide actionable recommendations — likely `full_name`, `standard`, `status`, and `date_of_birth`.

## Gallery URL validation gap

The POST `/api/gallery` endpoint validates that `url` is a string under 2048 characters but does not validate the URL scheme:

```typescript
if (typeof url !== 'string' || !url.trim() || url.length > 2048) {
  res.status(400).json({ error: 'A valid image URL is required (max 2048 characters).' });
  return;
}
```

The frontend renders this URL directly in an `<img src>`:

```tsx
<img src={img.url} alt={img.caption || 'School gallery image'} ... />
```

While modern browsers won't execute `javascript:` in `<img src>`, a `data:text/html;base64,...` URL or certain malformed URLs could cause unexpected behavior. More importantly, if gallery URLs ever appear in an `<a href>` context (e.g., "view full size" link added later), the XSS surface becomes real. Adding server-side validation that `url` starts with `https://` or `http://` closes this off proactively.

The endpoint is only accessible to `web_creator` and `principal` roles, so exploitation requires a compromised admin account — low-urgency but worth fixing as defense-in-depth.

## Security logs access inconsistency

The `/api/admin/security-logs` endpoint restricts to `['web_creator']` only, while other admin-level actions (gallery CRUD, student management) also allow `principal`. If a principal can view the SuperAdminCenter UI but cannot load the audit tab, they'll see an error. This is a UX inconsistency, not a security gap — worth aligning one way or the other.

## Migration not applied remotely

The `gallery_images` table doesn't exist in the live Supabase instance yet (documented in FEAT-001 findings). The frontend handles this gracefully — `galleryImages` stays empty, the section doesn't render. The `/api/gallery` POST/DELETE endpoints will return 500 errors until the migration is applied manually. The gallery feature is effectively dead on deploy until then.
