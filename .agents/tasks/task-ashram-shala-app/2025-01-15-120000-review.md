# Greenfield tribal school management system — React + Express SPA

A full-stack SPA for the Shashkeey Madhyamik Ashram Shala Pathraj, a government tribal residential school in Raigad district. The system provides role-based portals for admissions, attendance, hostel management, WhatsApp communications, clerk workflows, and a super-admin center — all bilingual (Marathi/English). The implementation uses React 18 with Vite, Express as the backend, Tailwind CSS v4 for styling, and `motion/react` for animations. All data is currently mocked in-memory (520 students, 41 staff, 52 hostel rooms).

Watch for: the role-switching mechanism is entirely client-side with no server-side enforcement (confirmed), the AI chat endpoint swallows API keys without validation or error differentiation (confirmed), the Aadhaar "verification" is a 2-second timeout with no actual verification logic (confirmed), and the `AppContent` component calls `setActiveTab` during render which will cause an infinite re-render loop under certain role-switch conditions (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The architecture is a single Express server that serves Vite-compiled React in dev mode and static files in production. The backend has three stub API routes (`/api/students`, `/api/staff`, `/api/ai-chat`); all real logic lives in the React layer. Data doesn't persist, there's no database, and no real integrations exist yet.

Role-based access control is implemented exclusively in the browser via React context. The user can switch roles from a dropdown in the header; no authentication, no token, no server-side gate. This would be a critical vulnerability if deployed with real student data (Aadhaar numbers, tribal certificates, mobile numbers are all modeled in the types).

The `AppContent` component has a state-during-render bug: when the user switches roles such that the current tab becomes invisible, `setActiveTab` is called during the render phase (outside an effect), which will trigger a React warning and potentially an infinite loop in strict mode.

The bilingual mechanism is a `t(en, mr)` helper per component with all translations inline — no shared i18n file. Every new string requires touching the component file directly rather than a centralized translation resource.

Aadhaar-like 12-digit numbers are generated and stored in plain text in the mock data. When this moves to real data, these fields need encryption at rest and access-scoped retrieval on the server.

<details>
<summary>Issues (7)</summary>

1. **setState during render in AppContent** — The tab-visibility guard calls `setActiveTab` during the render body. Move this logic to a `useEffect` or compute the effective tab without mutating state during render.
2. **No server-side RBAC** — Role enforcement is purely client-side React context. Any API route serves all data regardless of the caller. Before deploying with real data, add authentication middleware and role checks on the server.
3. **Fake Aadhaar verification** — `handleAadhaarVerify` fakes success after a timeout. The UI presents a green checkmark with "Verified" status, which could mislead users into thinking verification occurred. Add a clear "(Demo)" label or wire to an actual verification service.
4. **AI chat error handling is opaque** — The `/api/ai-chat` endpoint returns a mock response and the client falls back to random canned responses on network errors. There's no distinction between "no API key configured" and "service is down," giving the user no actionable feedback.
5. **Mobile bottom tab bar truncates portals** — `visibleTabs.slice(0, 5)` hard-codes showing only the first 5 tabs in the mobile bottom bar; remaining portals (AI Assistant, Docs, Admin) are only accessible via the hamburger menu. The discoverability gap is worth addressing.
6. **No test coverage** — Zero test files exist. The type-checking (`tsc --noEmit`) passes, but there are no unit tests, integration tests, or e2e tests for any component or API route.
7. **PII in mock data** — Generated Aadhaar-like numbers, mobile numbers, and tribal caste categories flow through the client. When moving to real data, these fields need encryption at rest and access logging on the server.

## setState during render in the tab router

In `App.tsx`, the `AppContent` component's render body contains:

```tsx
const visibleTabs = tabs.filter(tab => tab.roles.includes(role));

if (!visibleTabs.find(t => t.key === activeTab) && visibleTabs.length > 0) {
  setActiveTab(visibleTabs[0].key);
}
```

This calls `setActiveTab` synchronously during render. React 18 in strict mode will double-invoke the render, causing the state update to re-trigger rendering in a loop. The fix is either `useEffect` with `[role, activeTab]` dependencies, or computing the effective tab derivatively (e.g., `const effectiveTab = visibleTabs.find(…) ? activeTab : visibleTabs[0].key`) without ever calling setState in the render body.

## Client-only role-based access

The role system is defined in `AppContext.tsx` as a React state variable defaulting to `'web_creator'` (full access). The header provides a dropdown to switch roles, and each tab's `roles` array gates visibility:

- The Express server has no notion of who is calling. `/api/students` returns all 520 student records regardless.
- There is no login flow, no session, no JWT, no cookie.
- The `AppRole` type (`web_creator | principal | class_teacher | clerk | subject_teacher | student_parent`) doesn't map to the backend `Role` type (`principal | teacher | clerk | rector | support | mess_staff`), suggesting the frontend role system was designed independently of a future backend auth layer.

This becomes a data-leak issue the moment real Aadhaar numbers or tribal data enters the system.

## Aadhaar verification theater

`AdmissionPortal.tsx` provides a "Verify" button that, when 12 digits are entered, runs:

```tsx
const handleAadhaarVerify = () => {
  if (formData.aadhaar.length !== 12) return;
  setAadhaarVerifying(true);
  setTimeout(() => {
    setAadhaarVerifying(false);
    setAadhaarVerified(true);
  }, 2000);
};
```

This always succeeds. The green checkmark and "Verified" text imply the number was validated against a government API. The UI should indicate demo status, or the form submission should not gate on "verified" status if verification isn't real.

## Express API surface and its gaps

The server exposes three routes:

- `GET /api/students` — returns all mock students (no pagination, no filtering, no auth)
- `GET /api/staff` — returns all mock staff
- `POST /api/ai-chat` — accepts `{ message }`, returns a canned mock response

The `prdData.ts` documents additional endpoints (hostel allocate, mess mark, whatsapp send, student CRUD) that don't exist on the server. The frontend doesn't call any of these — it operates entirely on imported mock data via `import { students } from '../data/mockData'`. The Express server is essentially decorative for the current UI.

The AI chat endpoint has no rate limiting, no input sanitization, and the `.env.example` references `GEMINI_API_KEY` but the server never reads it. When Gemini integration is added, the API key needs validation on startup and chat responses should include proper error states (key missing, quota exceeded, service unavailable) rather than falling back silently.

## Device-mode access control in ClassTeacherPortal

The attendance portal has a "Device Mode" toggle that simulates "Whitelisted Desktop" vs. "Mobile Read-Only" restrictions:

```tsx
disabled={!isDesktop}
```

This is purely a UI toggle stored in component state. Any user can flip it. In production, device-mode enforcement would need to happen server-side (e.g., check device fingerprint or IP range against a whitelist).

## WhatsApp Hub — two disconnected chat interfaces

The `WhatsAppHub` component has a chatbot tab that uses local random responses from a fixed array (`botResponses`). The separate `AiAssistant` component calls `/api/ai-chat` on the server. A user might expect these to be connected. The WhatsApp chatbot doesn't hit any API and has no way to send real messages; the AI assistant hits the mock endpoint. Neither integrates with the WhatsApp Business API referenced in `.env.example`.

## Absence of tests

No test files, no test runner in `package.json`. The only verification is `tsc --noEmit`. Given the complexity of mock data generation (seeded PRNG, 520 students with specific distributions) and role-visibility logic, at minimum:

- Unit tests for the seeded mock data generator (verify determinism, correct distributions)
- Component tests for role-visibility filtering
- API route tests for the Express endpoints

would catch regressions as the system moves toward real data.
