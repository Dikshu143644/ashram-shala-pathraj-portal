# Portal enhancements: gallery storage, dual-password, admission form, AI data access

This commit adds several features to the Ashram Shala portal: Supabase Storage-backed gallery uploads replacing simple URL-based gallery entries, a dual-password system where users receive an auto-generated 6-digit AI PIN alongside their portal password, a public admission application form that saves to a new `applications` table, enhanced AI agent prompts with real data fetching (attendance, events, applications), and a "Navigate to School" button on the contact page. The admin center gains gallery management and applications viewing tabs.

Watch for: The AI PIN is returned in plaintext in the HTTP response body and displayed in the browser — if the user navigates away, they lose it permanently with no recovery path (confirmed). The public `/api/applications` endpoint has no rate limiting or CSRF protection, making it trivially spammable (confirmed). The gallery upload parses user-supplied content-type strings from the base64 data URI without allowlisting, which could store non-image content in the public bucket (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The dual-password mechanism piggybacks on the existing `set-password` endpoint — whenever a user sets their primary password, a random 6-digit PIN is bcrypt-hashed and stored in a new `ai_password_hash` column. The PIN is returned once in the JSON response and shown on-screen. There is no regeneration flow, no delivery to email/WhatsApp, and no way to retrieve it later. An attacker who compromises either credential gains full portal access since the login flow treats both as equivalent.

The gallery upload accepts a base64-encoded image body (up to 10 MB decoded), stores it in Supabase Storage under a `gallery/` prefix, and records the public URL and storage path in `gallery_images`. The content-type is extracted from the data URI prefix without validation, so any MIME string matching `image/[a-zA-Z+]+` passes through — including crafted types like `image/svg+xml` which can carry script payloads in a public bucket.

The admission applications endpoint is intentionally public (no auth) to let unauthenticated visitors apply. It validates field formats but has no `requireSameOrigin`, no rate limiter, and no CAPTCHA, so automated submissions are trivial.

The AI agent's system prompt now instructs Marathi-first response ordering and includes real school contact info and navigation links. At runtime it attempts to query `attendance`, `events`, and `applications` tables — all wrapped in try/catch with silent fallback — but the prompt tells the AI to produce data-driven recommendations even when no data was fetched, which may yield hallucinated analysis.

<summary>Issues (7)</summary>

1. **AI PIN unrecoverable after page navigation** — The 6-digit PIN is displayed once on-screen with no email/WhatsApp delivery and no regeneration endpoint. Add a `/api/auth/regenerate-ai-pin` endpoint or send the PIN via the existing Resend integration.
2. **AI PIN brute-forceable** — 6-digit numeric PINs have 900,000 possible values. The login endpoint's per-user rate limit should be verified to be aggressive enough (≤5 attempts/minute) or the PIN space should be expanded to alphanumeric.
3. **Applications endpoint lacks rate limiting** — `POST /api/applications` uses only `dataGate` (Supabase connectivity check). Add `writeLimit` and `requireSameOrigin` or an equivalent public-submission rate limiter.
4. **Gallery upload accepts unvalidated content-type** — The regex `image/[a-zA-Z+]+` allows `image/svg+xml` and other dangerous types. Allowlist to `image/jpeg`, `image/png`, `image/webp`, `image/gif`.
5. **AI prompt promises data-driven output without guaranteeing data** — When attendance/events tables don't exist, the prompt still instructs analysis. Add a preamble like "No student data available" when context queries return empty so the model doesn't fabricate.
6. **Storage deletion is fire-and-forget** — `supabase.storage.remove()` result is not checked; if storage deletion fails, the DB row is still deleted, leaving orphaned objects.
7. **No gallery_images migration for `url` column** — The upload endpoint writes a `url` field but the migration only adds `storage_path`. If `gallery_images` was created in a prior migration without `url`, this works; if not, the insert will fail silently.

## Dual-password system and PIN lifecycle

The AI PIN is generated inside the `set-password` handler (server/auth.ts ~line 848). Every time a user sets a password — whether on first registration or via the "must change password" flow — a new PIN is generated and overwrites the previous one. Changing your portal password silently rotates your AI PIN with no notification.

```typescript
res.json({ success: true, aiPin });
```

The PIN is displayed once in `RegisterPage.tsx`. If the user closes the tab or navigates away, the PIN is gone permanently.

The login fallback (auth.ts ~line 310) issues a separate query to fetch `ai_password_hash` only if the primary password comparison fails. This creates a timing oracle: login with the correct primary password returns faster than login with the AI PIN because the AI PIN path does one extra Supabase query. Likely not exploitable given network jitter, but it reveals which password type was used.

The 6-digit numeric PIN has only 900,000 possible values. If the per-IP or per-user rate limit on the login endpoint allows more than a few attempts per minute, the PIN is brute-forceable within hours.

## Gallery upload: stored-XSS via content-type

The upload endpoint extracts content-type from the data URI:

```typescript
const base64Match = image.match(/^data:(image\/[a-zA-Z+]+);base64,(.+)$/);
```

This regex accepts `image/svg+xml`, which Supabase Storage will serve with that content-type to any browser hitting the public URL. SVG files can contain `<script>` tags — this is a stored-XSS vector. Fix: allowlist to `image/jpeg`, `image/png`, `image/webp`, `image/gif`.

The DELETE handler calls `supabase.storage.remove()` but discards the result. If storage deletion fails (network error, bucket misconfiguration), the metadata row is still deleted, leaving an orphaned object that consumes quota indefinitely.

## Public applications endpoint — spam surface

`POST /api/applications` is registered with only `dataGate` middleware:

```typescript
app.post('/api/applications', dataGate, async (req, res) => { ... });
```

Other write endpoints in this file use `requireSameOrigin` and `writeLimit`. This endpoint has neither. The mobile number regex `[6-9]\d{9}` provides minimal friction — an attacker can script thousands of fake applications with valid-looking mobiles. Given this is a government school portal with limited admin bandwidth, even moderate spam would be disruptive.

## AI agent data context — hallucination risk

The agent route (server/agents.ts ~line 230) attempts three additional queries for authenticated parents:

1. `attendance` table — last 30 records for linked students
2. `events` table — next 10 upcoming events
3. `applications` table — by the user's mobile number

Each is individually try/caught with silent fallback. If all three tables don't exist or return empty, `studentContext` may contain only the raw student records. But the system prompt still instructs the model to "analyze attendance patterns" and "suggest specific next steps." The model has no way to know that missing data means unavailable (vs. perfect attendance), so it will fabricate recommendations.

Fix: append explicit "No attendance data available" / "No events data available" to the context when queries return null or empty arrays.
