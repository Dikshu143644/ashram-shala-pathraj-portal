# Portal enhancements v2: fixes applied for PIN delivery, rate limiting, content-type, hallucination guards

The fix commit addresses all seven issues raised in the v1 review: the AI PIN is now emailed via Resend after generation, the public applications endpoint has an IP-based rate limiter (5 requests per 10 minutes), gallery upload enforces a strict content-type allowlist (JPEG/PNG/WebP/GIF only), the AI context now appends explicit "no data available" markers when queries return empty, and storage deletion errors are logged before proceeding. The dual-password system, gallery upload, admission form, and AI data-fetching features are otherwise unchanged.

Watch for: The AI PIN is generated with `Math.random()` instead of `crypto.randomInt()`, making the PIN predictable if an attacker can observe or correlate server timing (likely). The applications endpoint still lacks `requireSameOrigin` middleware, so cross-origin form submissions are possible — rate limiting alone doesn't prevent targeted CSRF-style abuse (confirmed). The PIN is still returned in the HTTP response body *and* emailed, creating two exfiltration surfaces instead of one (possible — depends on threat model).

**Verdict**: APPROVED

## High-level view

The v1 PIN-recovery gap is closed: the set-password handler now sends the AI PIN to the user's registered email via Resend before returning the JSON response. If Resend credentials are missing or the send fails, the PIN still appears on-screen as a last resort and the failure is logged. The remaining concern is that `Math.random()` generates the PIN rather than Node's `crypto` module — acceptable given the 5-attempt rate limit, but inconsistent with the `randomBytes` usage elsewhere in the same file.

The applications endpoint now applies `publicWriteLimit` (5 per 10 minutes per IP), making bulk spam impractical. It still lacks `requireSameOrigin`, meaning cross-origin form submissions are possible — the rate limiter is the only defense against drive-by CSRF-style abuse.

The AI context injection now appends explicit "No data available" strings when queries return empty or throw, giving the model a clear signal to avoid fabricating data-driven recommendations.

## AI PIN generation: Math.random vs crypto

The PIN generation at server/auth.ts line 849:

```typescript
const aiPin = Math.floor(100000 + Math.random() * 900000).toString();
```

`Math.random()` uses a PRNG (V8's xoshiro128++) that is not cryptographically secure. In contrast, the same file uses `randomBytes(16)` (line 737) and `randomBytes(6)` (line 1052) for temporary passwords. The inconsistency suggests oversight rather than intent.

The practical impact is low: the 5-per-60s rate limit makes online brute-force infeasible regardless of the PIN's randomness quality. The concern is offline prediction — if an attacker knows the server's V8 PRNG state (e.g., from other observable random outputs), they could predict future PINs. This is a defense-in-depth concern, not an active exploit vector.

Fix: replace with `crypto.randomInt(100000, 1000000)` — one line change, zero performance impact, eliminates the concern entirely.

## Applications endpoint: rate-limited but open to cross-origin

The `publicWriteLimit` middleware (5 requests per 10 minutes per IP) prevents naive spam:

```typescript
app.post('/api/applications', publicWriteLimit, dataGate, async (req, res) => { ... });
```

Other write endpoints in the same file (`POST /api/gallery/upload`, `POST /api/gallery`) use `requireSameOrigin` as their first middleware. The applications endpoint omits it because it's intentionally public. However, "public" means "accessible without auth" — it doesn't necessarily mean "accessible from any origin." A CSRF attack could submit applications from a malicious page under the victim's IP, consuming their rate limit or creating spurious applications with their IP attribution.

Adding `requireSameOrigin` wouldn't break the admission page (same-origin requests pass through) and would block drive-by cross-origin submissions.

## PIN delivery: dual-channel exposure

The PIN is now exposed in both the HTTP response JSON (`res.json({ success: true, aiPin })`) and the email (plaintext and HTML). The response body is visible in browser devtools, JavaScript memory, and any client-side logging. A more conservative approach: return `{ success: true, aiPinDelivered: true }` and let the UI show "Your AI PIN has been sent to your email" without displaying the PIN in the DOM. This reduces the attack surface to the email channel alone.
